# Новая фича по слоям

Чек-лист. Слои и их границы — раздел Architecture в `CLAUDE.md` и раздел 6.2 `docs/spec.md`; здесь они не повторяются. Прочитай их перед началом.

## План

Фича больше одного файла — сначала план, потом код. План **двухуровневый с самого начала**:

- `docs/plans/stage-<N>-<имя>.md` — то, что читают перед каждой частью: контекст, решения, части, сводка «пункт → тесты», риски. Это и есть «план»; отметку `Статус: выполнен` ставит `/finish-stage` только сюда.
- `docs/plans/stage-<N>-<имя>-notes.md` — то, что пишут и редко перечитывают: аудит читателей (если был), пробы шага 0 (вопросы и результаты), таблицы проверок на зубы, итоги реализации каждой части. Создай файл сразу, с заголовками-заготовками. В основном плане от каждого такого блока остаётся ссылка и 1–3 строки вывода (что поменялось в решениях).

**Как работать с планом:**

- План читается **по разделам**, не целиком: `grep -n '^#' docs/plans/stage-<N>-<имя>.md` для карты, затем `Read` с `offset`/`limit` на нужный раздел. Целиком читается только на планировании.
- **Каждая часть этапа — отдельная сессия** (A, B…), а не продолжение предыдущей: контекст чист, а итоги прошлой части лежат в notes и в блоке «Итог» плана. Часть большая — `/compact` на внутренней границе между слоями, а не посреди шага.
- **Ревью и правки по нему — в начале свежей сессии**, а не в хвосте длинной.

Структура основного плана:

1. **Контекст** — зачем, что уже есть, цель списком.
2. **Решения** — нумерованные, каждое с причиной и отвергнутой альтернативой. На них ссылаются ревью (`[contradicts plan]`) и код.
3. **Разбор** — что меняется по слоям (шаги 1–6 ниже); независимые куски — отдельные части с отдельными PR.
4. **Сводка «пункт → тесты»** — каждый пункт плана → какие тесты его покрывают (юнит с фейком, дымовой на реальной ссылке, ручная проверка). Пункт без теста — явно, с причиной.
5. **Риски** — что может не сработать и что делаем тогда.

Правила:

- **Шаг 0 «Разведка → стоп».** Если в плане есть неизвестные (лимиты Telegram, что yt-dlp возвращает для этого типа публикации, нужна ли перекодировка), первым шагом идут пробы в scratchpad, не в коммитах. Результаты — в notes (раздел «Пробы шага 0»; выводы, меняющие решения, — в план). После разведки **остановись и покажи пользователю итог**, не продолжай к коду, пока решения не пересмотрены с учётом найденного.
- **Проба — это запуск на реальной системе** (настоящий yt-dlp на публичной ссылке, отправка в тестовый чат, файл на диске), а не чтение документации. Числа лимитов в коде — только из проб, с ссылкой на запись в notes.
- **Аудит читателей до нового значения во внешних данных.** Фича читает новое поле Telegram `Update`, новый ключ словаря yt-dlp или меняет формат JSON в `data/` — первым шагом перечисли всех читателей (`grep` по ключу, по `json.load`, по разбору `info_dict`/`entries`, по обработчикам апдейтов) и для каждого запиши, что будет при отсутствующем поле, `None`, незнакомом значении и старом формате файла. Ожидаемое поведение — пропустить с записью в лог, а не упасть и не потерять остальные данные (например, список разрешённых групп). Таблица — в notes плана.
- **Отклонения идут обратно в план.** Реализация разошлась с планом — поправь план в том же коммите (решение, шаг или риск) и пометь, что изменилось. Меняющее решение, шаг или риск — в основной план; подробности прогона (таблицы зубов, логи, список упавших тестов) — в notes.
- Статус плана: строка `**Статус: выполнен** — PR` ставится в `/finish-stage` в основной план (не в `-notes.md`), вручную не нужна.

## 1. Разбор ссылок

- [ ] Чистые функции без сети: поиск ссылок в тексте, нормализация (параметры, завершающий `/`, варианты доменов).
- [ ] Тесты таблицей: каждый вариант ссылки → ожидаемый результат; плюс ссылки, которые **не** должны распознаваться (положительный контроль рядом).

## 2. Маршрутизация

- [ ] По нормализованной ссылке — платформа и тип публикации, выбор загрузчика только через порт.
- [ ] Тесты: каждый тип → нужный загрузчик; неподдерживаемая ссылка → понятный отказ, а не исключение.

## 3. Загрузчик (порт)

- [ ] Интерфейс и общие структуры результата (медиафайлы с типами и порядком, описание, временный каталог) — без типов yt-dlp и aiogram.
- [ ] Реализация поверх `yt-dlp` как библиотеки: вызовы блокирующие — через `asyncio.to_thread`; тайм-аут; свой временный каталог на загрузку.
- [ ] Ошибки yt-dlp → ошибки порта (недоступно, нужна авторизация, слишком большой файл, прочее). Значения cookies и токены — не в лог.
- [ ] Фейк загрузчика для тестов возвращает заданные файлы или ошибки и ведёт себя как реальная реализация (те же типы ошибок, порядок, очистка каталога).
- [ ] Дымовой тест на реальной публичной ссылке — в сводке плана (не в CI).

## 4. Отправка

- [ ] Результат загрузки → вызовы Telegram: видео, фото, медиагруппы с разбиением, подпись с учётом лимита (лимиты — из проб).
- [ ] Временный каталог удаляется в `try/finally` при любом исходе отправки, включая отмену.
- [ ] Тесты с фейком Telegram: разбиение, порядок, обрезка подписи, ошибка отправки не роняет остальное.

## 5. Обработчик aiogram

- [ ] Тонкий: проверка доступа до любой работы → вызовы слоёв 1–4 → короткое сообщение об ошибке пользователю, причина в лог.
- [ ] Ошибка одной ссылки не мешает остальным ссылкам сообщения и не останавливает бота; `CancelledError` не глотается.
- [ ] Незнакомый тип апдейта, пустой `text`/`caption` — пропуск, а не исключение.

## 6. Доступ и хранилище

- [ ] По умолчанию всё запрещено, пока владелец не разрешил группу.
- [ ] Запись JSON в `data/` — атомарно (временный файл + `os.replace`); чтение терпимо к незнакомым ключам и старому формату (см. аудит читателей).
- [ ] Тесты: прерванная запись не портит список; неразрешённая группа игнорируется (и парный положительный контроль для разрешённой).

## 7. Проверка

- [ ] Все проверки запускай через субагента `check-runner`, а не в основной сессии; решение принимай по коду возврата из его отчёта, а не по формулировкам.
- [ ] `scripts/check.sh` целиком (lint, hooks, test).
- [ ] **Проверка на зубы.** Для каждого нового теста назови строку продакшен-кода, без которой он упадёт, и убедись: временно сломай её (инверсия условия, удаление вызова; откат — `git checkout -- <файл>`) и прогони тест — он должен покраснеть. Не покраснел — тест ничего не проверяет. Докстринг и имя теста не обещают больше, чем проверяют ассерты; проверка «не произошло X» имеет парный положительный контроль («X происходит в таком же сценарии»). Таблица «мутация → упавшие тесты» — в notes плана. Мутации — **по одной на прогон и по одной ветке разбора**: у каждого терпимого читателя свой тест, названный по нему.
- [ ] `py-reviewer` на diff.
- [ ] Появился новый слой или правило — обнови раздел Architecture в `CLAUDE.md`.

## Особенности платформы

Пополняется уроками этапов (через `/finish-stage`). Сюда — только факты, подтверждённые пробой, со ссылкой на notes этапа.
