# Завершение этапа

Аргумент — номер PR (`$ARGUMENTS`); если не передан, возьми PR текущей ветки (`gh pr view --json number,url,headRefName`). План этапа — `docs/plans/stage-*.md`, на который ссылается PR.

Всё, что фиксирует итог этапа, идёт **последним коммитом в ветку этапа до слияния**: номер PR уже известен, отдельной ветки и отдельного PR не нужно. Шаги идут по порядку; на любой неудаче остановись и расскажи пользователю, что именно не прошло.

**Этап из нескольких PR** (части A, S, B…): запись журнала, отметка плана и итоговый коммит идут **последним коммитом в PR последней части до её слияния**, а не отдельным PR; в отметке плана перечисли номера всех PR. Если все PR уже слиты — итоги идут в отдельную ветку и PR (отклонение от правила, скажи об этом пользователю).

## 1. Исходное состояние

- [ ] `gh pr view N --json state,headRefName,url` — PR открыт; запомни `headRefName` и `url`.
- [ ] `git switch <headRefName>` и `git status` — ты на ветке этапа, дерево чистое, нет отставания от `origin/<headRefName>` (`git pull`, если есть).

## 2. Запись в `docs/lab-journal.md`

Допиши в конец файла секцию (формат — как у существующих записей: `## <дата> · <заголовок>`):

```
## <YYYY-MM-DD> · Этап N: <название>
Сделано: <что вошло, 2–4 строки, со ссылкой на PR>
Сломалось: <что падало по пути: сборка, CI, ревью, неверные допущения плана; «ничего», если так>
Уроки: <по пункту на урок, каждый — правило, применимое к следующему этапу>
```

Источники: план этапа, `git log master..HEAD` (коммиты правок по ревью), замечания ревью в PR (`gh pr view N --comments`), прогоны `scripts/check.sh`. Не выдумывай: если факта нет в этих источниках — спроси пользователя. Слияния в записи ещё нет — не пиши, что PR слит.

## 3. Закрепление уроков

Для **каждого** урока предложи, куда его закрепить, и спроси пользователя (AskUserQuestion, по одному вопросу на урок или группой до 4):

| Куда | Когда |
|---|---|
| `CLAUDE.md` | правило для любой работы в репозитории; короткое, проверяемое |
| скилл (`.claude/skills/`) | шаг или ловушка конкретного процесса (новая фича, завершение этапа) |
| агент (`.claude/agents/`) | что ревьюеру стоит проверять |
| тест / `scripts/check.sh` | урок можно превратить в автоматическую проверку — предпочтительный вариант |
| никуда | единичный случай; остаётся только в журнале |

Для каждого урока дай рекомендацию и причину в одну строку. Применяй только то, что пользователь подтвердил. Правки обвязки (`.claude/`, `CLAUDE.md`, `scripts/`) — отдельными коммитами **до** итогового; если подтверждённые правки меняют код проекта, прогони `scripts/check.sh` нужной секции.

## 4. Отметка в плане

В основном плане `docs/plans/stage-N-<имя>.md` (не в `…-notes.md`, если план двухуровневый; для этапа из нескольких PR — со всеми номерами) сразу под заголовком поставь строку:

```
**Статус: выполнен** — [PR #N](<url PR>), <YYYY-MM-DD>
```

Если строка уже есть (план был в работе) — замени её. Хук SessionStart (`.claude/hooks/session-context.sh`) ищет именно `Статус: выполнен`, так что формулировку не менять.

## 5. Итоговый коммит и push

- [ ] Один коммит с записью журнала и отметкой плана (`git add docs/lab-journal.md docs/plans/stage-N-<имя>.md`), он последний в ветке.
- [ ] `git push` — в ту же ветку, PR обновится сам. Новых веток и PR не создавать.

## 6. CI и merge

- [ ] Дождись CI на новом коммите: `gh pr checks N --watch` (запусти в фоне и жди уведомления, не опрашивай в цикле). Красные проверки — стоп: merge не делать, показать список.
- [ ] `gh pr view N --json mergeable,state` — PR сливается без конфликтов.
- [ ] `GH_PROMPT_DISABLED=1 gh pr merge N --merge --delete-branch`
- [ ] `git switch master && git pull`; убедись, что дерево чистое и `git log -1` — merge-коммит этого PR.
