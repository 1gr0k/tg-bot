# Этап 1 — сквозной конвейер

План двухуровневый: подробности проб, таблицы зубов и итоги частей — в
[`stage-1-pipeline-notes.md`](stage-1-pipeline-notes.md). Читать по разделам: `grep -n '^#'`.
Числа лимитов в этом плане — **ожидания для проверки пробами**, не значения для кода.

## 1. Контекст

Кода бота нет; есть платформа этапа 0 (`scripts/check.sh`, хуки, агенты, скиллы). Полный
`check.sh` красный: тестов нет (pytest 5). Репозиторий на GitHub (`1gr0k/tg-bot`), CI нет.

Цель этапа:
- сквозной конвейер в личном чате с владельцем: ссылка → разбор → маршрутизация → загрузчик →
  отправка; YouTube Shorts, Instagram Reels, Instagram Posts (фото, видео, карусель);
- доступ: только личный чат с `OWNER_ID`; всё остальное — пропуск с записью в лог;
- защита секретов в git (gitleaks pre-commit + CI) — до первого кода с токеном;
- CI на GitHub Actions: lint, hooks, test, gitleaks.

Бот — существующий, старый токен; состоит в группах прошлой версии. Из групп не выходим (этап 2).

## 2. Решения

Все решения шага 0 закрыты пробами (notes, «Пробы шага 0»); ссылка «проба N» — на основание.

1. **Доступ этапа 1 — фильтр в outer-middleware Dispatcher**: апдейт проходит, только если это
   `message` из `chat.type == private` и `from_user.id == OWNER_ID`; иначе — выход без обработки.
   **Журнал проигнорированного** [проба 0: `can_read_all_group_messages=True` — бот получает все
   сообщения старых групп]: каждый проигнорированный апдейт — `DEBUG`; `INFO` — один раз на чат за
   время работы процесса (множество id чатов в памяти). В лог — только тип апдейта и id чата,
   **никогда текст**. Причина: иначе журнал заполняется перепиской чужих групп — и шум, и
   утечка. Тест: два апдейта из одной группы → одна `INFO`-запись; текст сообщения не попадает
   в лог (положительный контроль: тот же текст в разрешённом чате доходит до обработчика).
   Причина фильтра: проверка до любой работы в одном месте, этап 2 заменит функцию решения, а
   не обработчики. Отвергнуто: фильтр на каждом обработчике (легко забыть на новом); выход из
   групп сейчас (ТЗ 4.4 целиком — этап 2); `INFO` на каждый апдейт (поток записей).
2. **Накопленные апдейты при старте — сбрасываются** (`drop_pending_updates=True` в
   `start_polling`). Подтверждено пробой 0: 149 ожидающих, в выборке из 100 — все `message` из 3
   супергрупп прошлой версии, из личного чата владельца — 0, возраст 9–24 ч. Обработать их нечего,
   а при этапе 2 они дали бы поток выходов/запросов. Плюс `allowed_updates` — явно из
   `dp.resolve_used_update_types()`: на стороне Telegram сохранён старый список
   (`message, callback_query, my_chat_member`). Отвергнуто: обработать накопленное (на этапе 1
   всё равно пропуск, лишняя нагрузка и записи в лог).
3. **Временный каталог принадлежит вызывающему, а не результату**: конвейер создаёт каталог
   (`tempfile.TemporaryDirectory` в `try/finally` вокруг загрузки и отправки), загрузчик пишет
   только в переданный `workdir`. Причина: одно место очистки при любом исходе, включая отмену.
   Отвергнуто: `tmpdir` в `DownloadResult` (ТЗ 13) — утечка при исключении между созданием
   каталога и возвратом результата, владение размазано.
4. **Порт загрузчика — `Protocol` + frozen-dataclass результата + своя иерархия ошибок** без типов
   yt-dlp и aiogram (черновик — раздел 5). Отвергнуто: возвращать info dict yt-dlp (протечка).
5. **Один адаптер yt-dlp на платформу** (`InstagramDownloader`, `ShortsDownloader`) с общим
   модулем: опции, перевод ошибок, запуск в потоке. Reel и Post — один загрузчик Instagram,
   тип публикации — информация для лога. Отвергнуто: отдельный загрузчик Reels/Posts (ТЗ 13) —
   yt-dlp обслуживает оба одним экстрактором (подтверждено пробой 4).
   **Выбор формата — H.264 + AAC для Instagram и YouTube** (пробы 4, 5, `probe_send_media`):
   - Instagram — `b[format_id!*=dash]/bv*[vcodec^=avc1]+ba/bv*+ba/b`: прогрессивный H.264 + AAC в
     первую очередь. Селектор не зависит от `format_id` (с cookies id другие — `…v-2` вместо
     `3`, — выбор тот же). Отвергнуто: VP9 + AAC, который yt-dlp берёт по умолчанию. VP9 у
     владельца играет (iPhone и Telegram для Mac, `probe_send_media`), но если он не
     воспроизведётся на клиенте другого участника, бот этого не увидит — сбой невидим.
   - Shorts — `format_sort: ["vcodec:h264", "acodec:aac", "res:1080", "ext:mp4:m4a"]` +
     селектор с бюджетом размера (решение 9); `merge_output_format: "mp4"`, merge через FFmpeg,
     перекодировки нет. Отвергнуто: фильтр `height<=1080` (режет вертикальное видео); выбор по
     умолчанию (AV1/VP9 webm). Оригинальная аудиодорожка выбирается полем `lang` сортировки yt-dlp.
   - **Метаданные `MediaItem` (`width`, `height`, `duration`) — из ffprobe по скачанному файлу**:
     у прогрессивных форматов Instagram без cookies они в info dict `None`.
   - **Метаданные видео передаются в `sendVideo` / `InputMediaVideo` всегда** (`width`,
     `height`, `duration` из ffprobe, `supports_streaming=True`). `probe_send_media`: без них
     Telegram записал 320×320 и `duration=0` для двух H.264-файлов (Reel 73 с и Shorts 135 с),
     и **на iPhone эти видео растянуты в ширину**; с метаданными пропорции верные. Telegram для Mac
     растяжения не показывает — проверять только на Mac недостаточно. Тест: фейковая сессия
     проверяет поля `width`/`height`/`duration` запроса; ручная проверка этапа — на телефоне.
   - **Своя миниатюра не передаётся**: клиенты показывают кадр сами на всех видео, хотя API для
     части файлов возвращает `thumbnail=None` (те же два файла, и с метаданными). Пересмотр —
     если появятся пустые превью (например, при отключённой автозагрузке медиа у участника).
   - **Тип публикации — по ответу yt-dlp, а не по пути ссылки**: `/p/<код>` бывает фото,
     каруселью или одиночным видео (Instagram с 2022 года публикует одиночные видео как Reels,
     и Reel открывается и по `/p/`). Проба 4: `/p/DeRrI8_BTZz` и `/reel/DeRrI8_BTZz` дают
     одинаковый info dict (кроме URL) и один выбор формата. `PostKind` из разбора ссылки — только
     для лога; фото/видео/карусель — из `_type`, `entries` и пустых `formats`.
6. **Фото Instagram — внутри yt-dlp** (решено пробой 4): опция `ignore_no_formats_error=True`
   (без неё пост-фото → «There is no video in this post», а смешанная карусель падает целиком
   на фото-элементе); извлечение — `extract_info(download=False, process=False)`; элемент с
   пустыми `formats` — фото; URL — thumbnail без маркера размера (`[ps]<w>x<h>`) в параметре
   `stp` (оригинал; `width/height` у thumbnails нет); **немаркированного нет — вариант с
   наибольшим маркером** (по площади `w×h` из маркера); скачивание — `ydl.urlopen` (сеть,
   заголовки, cookies yt-dlp); видео-элементы — `process_ie_result` с селектором решения 5;
   порядок — порядок `entries`. **После загрузки — фактический размер картинки** (ffprobe):
   короткая сторона меньше 600 px → `WARNING` в лог (взят не оригинал — признак смены формата
   Instagram/yt-dlp), фото всё равно отправляется. Дымовой тест проверяет размер фото, а не только
   факт загрузки. Отвергнуто: aiohttp (вторая сетевая настройка рядом с yt-dlp — cookies,
   заголовки, прокси дублируются); gallery-dl (новая зависимость при рабочем пути в yt-dlp).
   Риск — в разделе 8.
   **Изменено по ревью части B — выбор URL и пропуск элементов.**
   - Выбор URL: если у миниатюры есть `width/height` (положительные целые) — берётся наибольшая по
     площади (равные — последняя), миниатюры без этих полей при этом не участвуют; нет — прежнее
     правило по маркеру `stp` (так сейчас: у Instagram `width/height` нет, проба 4). Причина:
     поля данных надёжнее догадки по параметру подписанного URL, если yt-dlp их начнёт отдавать.
   - **Элемент карусели, который не скачался или не годится (сверх лимита, ошибка загрузки,
     нет пригодных данных), пропускается** с `WARNING` в лог («элемент N из M пропущен: <тип
     ошибки>»); остальные элементы — в результате, порядок сохраняется. Файл сверх лимита, который
     yt-dlp всё же записал, удаляется сразу. В `DownloadResult` — поле `skipped` (число
     пропущенных; M = `len(items) + skipped`). Ни один элемент не удался — выбрасывается ошибка
     **первого** (одиночный Reel сверх лимита по-прежнему `MediaTooLarge`); нет ни ошибок, ни
     элементов — `NoMedia`. Прежнее поведение («видео-элемент сверх лимита → `MediaTooLarge` на
     всю публикацию») заменено: потеря одного элемента лучше потери всей карусели.
     `Cancelled` пропуском не становится. **Часть C:** пользователю — пометка «не удалось N из M»,
     когда `skipped > 0` (в `sending`/`pipeline`).
7. **Cookies Instagram — копия на каждую загрузку** (проба 4 с cookies): файл из
   `IG_COOKIES_FILE` копируется во временный каталог загрузки (права 600) и удаляется вместе с
   ним; `data/instagram.txt` yt-dlp не получает. Проба: yt-dlp **переписывает `cookiefile` при
   каждом запуске** и при сохранении **удаляет** `datr`, `ps_l`, `ps_n`, `wd`; меняются только
   `mid` и `rur`; `sessionid` не меняется. Отвергнуто: атомарная запись обратно (`os.replace` под
   `asyncio.Lock`) — ничего не продлевает (`sessionid` тот же) и портит исходник (теряются
   cookies); прямая передача исходника — та же порча плюс гонка параллельных загрузок.
   **«Cookies отвергнуты» — не по тексту ошибки** (проба 4, `--mode broken`): при испорченном
   `sessionid` yt-dlp пишет `[Instagram] <код>: Failed to parse JSON (caused by
   JSONDecodeError(…)); please report this issue…` — тот же текст будет при смене формата
   Instagram. Признак — **`sessionid` был в копии до загрузки и исчез после** (yt-dlp удалил его
   при сохранении) → `LoginRequired`; `sessionid` на месте при той же ошибке → `DownloadFailed`.
   Сравнение — по наличию имени в копии, значения не читаются в лог. Тест на фейковом cookies-файле:
   `sessionid` исчез → `LoginRequired`; `sessionid` на месте при той же ошибке → `DownloadFailed`
   (положительный контроль). Текст yt-dlp («please report this issue…») пользователю не
   показывается — пользователь получает `user_message` ошибки порта, причина — в лог.
   Без cookies (`IG_COOKIES_FILE` не задан) «Instagram sent an empty media response» →
   `LoginRequired` с текстом «недоступно без входа или удалено» (проба 4: различить нельзя).
8. **Тайм-аут загрузки**: `asyncio.timeout` вокруг `asyncio.to_thread`; при срабатывании —
   флаг `threading.Event`, который проверяет progress-hook yt-dlp (исключение прерывает загрузку),
   и ожидание завершения потока до удаления каталога. Плюс `socket_timeout=20`. **Тайм-аут
   загрузки одной ссылки — 120 с** (проба 6: 3–27 с с Mac/VPN, в том числе Shorts 135 с и Reel
   73 с; запас ×4; перепроверка на VPS). Отвергнуто: только `asyncio.timeout` — поток продолжает
   писать в удалённый каталог.
   **Изменено в части B (проба: progress-hook не вызывается на фазе извлечения, notes «Итог
   части B»).** Хук прерывает только загрузку; поток на фазе извлечения прервать нельзя, он живёт
   до конца извлечения (несколько запросов, каждый ограничен `socket_timeout`). Поэтому:
   1. При тайм-ауте адаптер ставит флаг отмены и **ждёт завершения потока** (`await future` под
      `asyncio.shield`), только потом выбрасывает `DownloadTimeout`. Решение 3 без исключений:
      каталогом владеет вызывающий, очистка — в одном `finally` после конца потока. **Цена:**
      время до ответа пользователю = тайм-аут (120 с) + хвост извлечения. Поток после флага
      живёт дольше порога (`3 × socket_timeout` = 60 с) — `WARNING` с длительностью, ожидание
      продолжается.
   2. **Свой `ThreadPoolExecutor`** с `max_workers` = лимит одновременных загрузок (решение 9: 2)
      вместо пула по умолчанию `asyncio.to_thread`: зависшие потоки yt-dlp не отнимают потоки
      у остального кода. **Семафор живёт в том же объекте (`ThreadRunner`) и отпускается только
      после завершения потока**, а не после тайм-аута ожидания (pipeline семафор не создаёт).
   3. `CancelledError` (остановка бота): флаг отмены, ожидание потока не дольше порога; не успел
      — `ERROR` в лог; `CancelledError` пробрасывается в любом случае.
   4. **Изменено по ревью части B — что выбрасывается после тайм-аута.** Если поток, дождавшись
      флага, завершился с `DownloadError` (например, `MediaTooLarge`), выбрасывается **она**, а не
      `DownloadTimeout`: это настоящая причина; в лог — `WARNING` с типом ошибки и длительностью.
      Иначе — `DownloadTimeout from <исключение потока>` (`Cancelled`, чужая ошибка; результат,
      пришедший слишком поздно, отбрасывается: `from None`). Срабатывание тайм-аута определяется
      самим `asyncio.timeout` (`expired()`), а не типом `TimeoutError`: собственный `TimeoutError`
      функции (сокет) — её ошибка, не `DownloadTimeout`. Исключение потока забирается
      done-callback'ом `future` всегда — и когда `run` уже не ждёт (остановка бота), иначе asyncio
      пишет «exception was never retrieved». Семафор освобождается и при ошибке потока, и при
      `CancelledError` (тест при `limit=1`: вторая загрузка стартует).

   Отвергнуто: **(B)** отдельный процесс для yt-dlp — убиваемый, но ещё один слой (передача
   результата и ошибок между процессами, импорт на каждую загрузку); **(C)** подмена сетевых
   функций yt-dlp — недокументированное устройство, ломается с обновлениями. **Пересмотр (B)** —
   если дымовые тесты на VPS покажут частые зависшие потоки.

   **Тайм-аут отправки файлов — отдельный**: `sendVideo`, `sendPhoto`, `sendMediaGroup`,
   `sendDocument` — `request_timeout=300` с; остальные запросы — тайм-аут сессии aiogram по
   умолчанию (60 с). Проба 1: 52 430 000 байт выгружались 14 с с Mac через VPN; на VPS скорость
   выгрузки неизвестна — запас ×20 (≈ 175 000 байт/с), перепроверка на VPS. Отвергнуто: один
   общий большой тайм-аут (зависший обычный запрос ждал бы минуты).
9. **Ресурсы (ТЗ 9.4)**: `asyncio.Semaphore` на одновременные загрузки (2); защита от повтора —
   множество «в работе» по нормализованной ссылке (повтор той же ссылки, пока идёт загрузка, —
   пропуск с логом).
   **Лимит размера видео** (проба 1): 50 500 000 байт — принято, 52 430 000 — `TelegramEntityTooLarge`
   (HTTP 413) **после выгрузки, через 14 с**; лимит — **52 428 800 байт**, граница между
   пробами. Проверка размера **до отправки** обязательна (иначе 14 с выгрузки впустую и ошибка).
   Все лимиты и уровни бюджета — **в байтах** (в коде и в плане, без МБ).
   **Бюджет в выборе формата** [проба 5: Shorts 135 с в 1080p — 58 440 000 байт]:
   - селектор опирается на `filesize`, запасной — `filesize_approx` (с меньшим порогом — оценка
     неточна), последний вариант — без размера:
     `bv*[filesize<V]+ba / bv*[filesize_approx<Va]+ba / b[filesize<T] / b[filesize_approx<Ta] / bv*+ba/b`
     (числа в фильтрах yt-dlp — байты, без суффиксов);
   - уровни бюджета `V`/`Va`/`T`/`Ta`, байт:
     1) 45 000 000 / 40 000 000 / 48 000 000 / 43 000 000;
     2) 25 000 000 / 22 000 000 / 28 000 000 / 25 000 000;
     3) 12 000 000 / 10 000 000 / 14 000 000 / 12 000 000.
     Запас под merge и неточность оценки (проба 5: `136+140` — файл 19 180 000 байт при
     `filesize` ≈ 16 900 000 + 2 200 000);
   - **после загрузки — фактический размер файла**: больше 52 428 800 → повтор со следующим уровнем
     бюджета (новый каталог внутри `workdir`); уровни кончились → `MediaTooLarge`. У прогрессивных
     форматов Instagram `filesize` нет — их ловит только эта проверка; `max_filesize` yt-dlp —
     дополнительная страховка на загрузку.
   - **Изменено по ревью части B.** *Instagram — без повтора по бюджету*: сверх лимита — сразу
     `MediaTooLarge`. Причина: H.264 у Instagram бывает только прогрессивным (один файл), варианты
     ниже по размеру — DASH VP9, отвергнутый решением 5; повтор дал бы тот же файл или VP9. Тест:
     одна загрузка, один набор опций. *Shorts — цена повтора*: каждый уровень бюджета — новый
     `YoutubeDL` и полное извлечение + загрузка (до трёх за обращение, проба 6: 3–27 с на
     попытку); все уровни — под одним тайм-аутом 120 с (решение 8), поэтому худший случай (три
     попытки по ~27 с) укладывается, но не с большим запасом — следить на VPS.
   - **Изменено по ревью части B — «файла нет» не равно «слишком большой».** yt-dlp при пропуске
     по `max_filesize` пишет в `logger.debug` текст «File is larger than max-filesize (N bytes >
     M bytes). Aborting.» (проба: локальный сервер, yt-dlp 2026.08.19; без исключения и без файла).
     `YdlLogger` ловит это сообщение и ставит флаг на попытку/элемент; **правило**: «файла нет»
     без флага — `DownloadFailed` (сбой yt-dlp, повтор по бюджету не нужен), с флагом —
     «слишком большой» (следующий уровень / `MediaTooLarge`); размеры из сообщения — в лог.
     Тесты: оба случая у Instagram и Shorts, фейк `YoutubeDL` шлёт то же сообщение тем же путём.
   - Тесты на фейке (часть B): формат без `filesize` (выбран вариант без размера, факт в лимите —
     отправка; факт сверх — следующий уровень); формат, у которого факт больше обещанного
     (`filesize` 40 000 000, файл 55 000 000 байт → следующий уровень); все уровни сверх лимита →
     `MediaTooLarge`.
     Перевод бюджета в строку селектора — юнит таблицей.
   **Лимит фото** (проба 1): 10 485 760 байт (из текста ошибки Telegram); отдельно — ограничение
   пропорций (`PHOTO_INVALID_DIMENSIONS` на 300×7000). Фото сверх размера — сразу `sendDocument`;
   `PHOTO_INVALID_DIMENSIONS` — повтор как `sendDocument` (проба 1: откат работает в обоих
   случаях). В медиагруппе такой элемент выносится из группы и уходит документом после неё (с
   записью в лог). Известное ограничение: Telegram пережимает фото до 2560 px по большей стороне
   (проба 1: 3600×3600 → 2560×2560) — оригинал в полном разрешении не сохраняется; принимаем.
10. **Отправка — две части**: чистая функция `plan_sends(result, limits) -> list[Send]`
    (что и в каком порядке отправить) и тонкий исполнитель поверх aiogram `Bot`. Причина:
    разбиение и подписи тестируются таблицей без фейков. Отвергнуто: собственный порт Telegram
    поверх aiogram — фейк сессии aiogram уже даёт тест без сети (решение 13).
11. **Медиагруппы** (проба 2): максимум **10** элементов, 11 → `Bad Request: too many messages
    to send as an album`; смешанная группа (фото + видео) принимается; группа из одного элемента
    тоже принимается. Больше 10 — разбиение на группы почти равного размера (11 → 6+5, а не
    10+1) — **выбор вида** (две соразмерные группы читаются как одна публикация), а не обход
    ограничения. Один элемент — `sendVideo`/`sendPhoto` (у них `supports_streaming` и откат на
    документ, решение 9); порядок сохраняется.
12. **Подпись** (проба 3): plain text (`parse_mode=None` явно — проба 3: `<b>`, `_`, `*`, `[x](y)`
    дошли как есть). Лимиты — **подпись 1024, текст 4096, в символах Unicode (кодовых точках), не
    в UTF-16**: 1024 эмодзи (2048 единиц UTF-16) в подписи и 2049 эмодзи в тексте приняты,
    ASCII/кириллица 1025 и 4097 — `message caption is too long` / `message is too long`. В коде и
    `limits.py` — `len(str)`. Подпись видна у элемента, к которому прикреплена (проба 2: на первом —
    подпись группы). Влезает — подпись к первому элементу первой группы; не влезает — медиа без
    подписи + полный текст следующим сообщением(ями) с разбиением по 4096 по границе пробела.
    Тест: эмодзи на границе (1024 эмодзи — подпись; 1025 — отдельным сообщением).
    Отвергнуто: обрезка с «…» — ТЗ 5.4 предпочитает полноту; подсчёт в UTF-16 (проба 3 опровергла).
    **Добавлено по ревью части B — источник подписи.** Instagram: `description` верхнего уровня,
    иначе первого элемента карусели с описанием. Shorts: `description`, при пустом или из одних
    пробелов — `title`, иначе пустая подпись (ТЗ 2.4: «название или описание, если доступно»);
    текст берётся как есть, без обрезки (длинное описание — отдельным сообщением, см. выше).
13. **Фейк Telegram — подмена сессии aiogram** (`BaseSession`, записывает запросы, отвечает
    заданным), токен в тестах — `42:TEST` (не совпадает с правилом gitleaks). Причина: обработчики

14. **Разбор ссылок** — чистые функции над строками; кандидаты — `text`/`caption` и `url` из
    entities `text_link` (извлекает обработчик). Поддержка: `instagram.com` с `www.`/`m.`,
    `/reel/`, `/reels/`, `/p/`, вариант с именем пользователя `/<user>/(reel|p)/<code>`;
    `youtube.com/shorts/<id>` с `www.`/`m.`; параметры, фрагмент и `/` в конце отбрасываются;
    дубликаты в одном сообщении схлопываются; не больше 5 ссылок на сообщение.
    **Ключ схлопывания дубликатов — `(platform, media_id)`**, а не `url`: `/reel/X` и `/p/X` — одна
    публикация, остаётся первая по порядку ссылка (изменено по ревью части A: решение принято при
    реализации, в плане не было). **Конец кода публикации — по ASCII-классу `[A-Za-z0-9_-]`, не по
    `\w`**: в Python `\w` включает кириллицу, и `…/reel/ABC123посмотри` не находилось (изменено по
    ревью части A).
    `youtu.be/<id>` — не поддерживается (это ссылка на обычное видео, ТЗ 2.4).
    `/p/<код>` не означает «фото или карусель» — тип публикации определяет загрузчик по ответу
    yt-dlp (решение 5).

    понятную ошибку при старте]: значения обрезаются от пробелов и `\r` (`.env` с CRLF);

    пустое, отсутствует, `OWNER_ID` не число — каждая строка → `ConfigError` с именем переменной,

    не-комментарная (и не пустая) строка файла `IG_COOKIES_FILE` — ровно 7 полей через табуляцию,
    `expires` (пятое) — только цифры; иначе `ConfigError` с номером строки и причиной, без
    содержимого строки (в ней значения cookies). Причина: yt-dlp молча пропускает строки не того
    формата — бот стартует «с cookies», а ошибка «нужен вход» приходит на первой загрузке без
    объяснения. `cookie_names` (решение 7) считает имя только в строке из ровно 7 полей — так же.
    Тесты: таблица (6/8/1 поле, пробелы вместо табуляции, `expires` пуст/буквы/минус/дробь, CRLF,
    HttpOnly, номер строки) и положительные контроли; значение cookie собрано в рантайме и не
    попадает ни в ошибку, ни в лог.
17. **Зависимости**: `uv add 'aiogram>=3.31.0,<4' 'yt-dlp[default,deno]>=2026.8.19'`

    предупреждает «YouTube extraction without a JS runtime has been deprecated, and some formats
    may be missing»; с `yt-dlp[default,deno]` (deno 2.9.7, yt-dlp-ejs 0.8.0) предупреждения нет,

    обновление только через `uv lock --upgrade-package yt-dlp` (ТЗ 10). В CI — `uv lock --check`.

    в Dockerfile (версия вне `uv.lock`, отдельное обновление). Проверить на этапе Docker: колесо

    `cookies` формата и в `http_headers` (заголовок `Cookie`). Функция `scrub(info)` рекурсивно
    удаляет ключи `cookies` и `http_headers` на любой глубине (форматы, `entries`,
    `requested_formats`), подписанные URL CDN (`url`, `manifest_url`, `thumbnails[].url` с
    параметрами подписи — `oh=`, `oe=`, `_nc_*`, `sig`, `expire` и т.п.) заменяет заглушкой
    `<signed-url>`.
    - В скриптах проб — **до** любой печати и сохранения JSON.
    - В части B — `tests/scrub.py` (утилита для подготовки фикстур) с тестом: info dict с
      `cookies`/`http_headers` на нескольких уровнях и подписанным URL → в результате их нет
      (положительный контроль: без `scrub` тест находит их). **Изменено в части B:** заглушка
      сохраняет параметр `stp` (`<signed-url>?stp=…`) — это маркер размера картинки, не секрет, а
      без него фикстуры не годятся для разбора фото (решение 6); подписанным считается любой
      строковый http(s)-URL с параметром подписи — в query **или в пути** (YouTube кладёт
      `sig`/`ip`/`expire` в путь), а не только известные ключи.
    - Фикстуры в `tests/` — только из очищенного вывода. Правило gitleaks на `sessionid`
      (решение 18) — второй слой.

    одной точки отказа — ради качества нескольких длинных роликов. Пересмотр — если дымовые тесты
    или журнал покажут частые `MediaTooLarge` или 720p окажется неприемлемым.

Общее для скриптов с секретами: токен — только `os.environ["BOT_TOKEN"]`, cookies — путь из

- Shorts: выбор формата — `format: "bv*+ba/b"` + `format_sort: ["vcodec:h264", "acodec:aac",

  yt-dlp по умолчанию не отдаёт, смешанная карусель падает целиком; путь через
  `ignore_no_formats_error` + оригинальный thumbnail + `ydl.urlopen` работает (→ решение 6).
- Shorts 135 с в 1080p — 58 440 000 байт, больше лимита (→ решение 9: бюджет размера в селекторе);
  при двух аудиодорожках выбирается оригинальная.
- Проба 0: 409 нет; privacy mode выключен — бот читает все сообщения старых групп (→ решение 1);

  (→ решение 16: проверка формата).
- Пробы 1–3 (пользователь): видео — лимит 52 428 800 байт, 413 после выгрузки (→ решение 9:
  проверка до отправки, уровни бюджета); фото — 10 485 760 байт и ограничение пропорций, откат на документ работает
  (→ решение 9); медиагруппа — максимум 10, одиночная принимается (→ решение 11); подпись 1024 и

- `/p/` с одиночным видео = тот же Reel: info dict и формат совпадают (→ решения 5, 14).
- `yt-dlp[default,deno]` убирает предупреждение о JS-рантайме (→ решение 17).
- Проба 4 с cookies (пользователь): yt-dlp переписывает `cookiefile`, удаляет часть cookies,

- `probe_send_media` + проверка на iPhone и Mac: VP9 играет, но выбран H.264 (→ решение 5); без
  метаданных два видео растянуты на iPhone (→ решение 5: метаданные всегда); превью есть везде

**Изменено по ревью части B — семафор и `ThreadRunner`.** Ограничение «2 одновременные загрузки»
(решение 9) — семафор внутри `ThreadRunner` (`downloader/ytdlp.py`), а не в `pipeline.py`:
семафор должен отпускаться по завершении **потока**, а не по тайм-ауту ожидания (решение 8), и знает
об этом только раннер; pipeline семафор не создаёт. **Один общий `ThreadRunner` на оба адаптера**
(`InstagramDownloader` и `ShortsDownloader` получают один экземпляр — иначе лимит удваивается:
2 + 2); создаётся один раз при запуске бота (часть C: `__main__`/сборка зависимостей), закрывается
`close()` при остановке. **Ожидание семафора не входит в тайм-аут 120 с**: отсчёт начинается после
получения места (`asyncio.timeout` внутри `async with sem`); третья ссылка при двух занятых местах
ждёт без ограничения времени ожидания — это очередь, не ошибка загрузки (ограничивать её
не нужно: бот — личный чат владельца на этапе 1).

## 5. Интерфейс порта (черновик, без реализации)

```python
class Platform(StrEnum): INSTAGRAM = "instagram"; YOUTUBE = "youtube"
class PostKind(StrEnum): REEL = "reel"; POST = "post"; SHORTS = "shorts"

@dataclass(frozen=True, slots=True)
class Link:
    platform: Platform
    kind: PostKind
    media_id: str          # shortcode / video id
    url: str               # нормализованная каноническая ссылка

class MediaKind(StrEnum): PHOTO = "photo"; VIDEO = "video"

@dataclass(frozen=True, slots=True)
class MediaItem:
    kind: MediaKind
    path: Path             # внутри workdir
    width: int | None = None
    height: int | None = None
    duration: float | None = None      # секунды, для видео

@dataclass(frozen=True, slots=True)
class DownloadResult:
    items: tuple[MediaItem, ...]       # исходный порядок, не пусто
    caption: str                       # "" — описания нет

class Downloader(Protocol):
    async def download(self, link: Link, workdir: Path) -> DownloadResult: ...

class DownloadError(Exception):        # базовая; user_message — короткий текст пользователю
    user_message: ClassVar[str]
class MediaNotFound(DownloadError): ...      # удалено / не существует
class LoginRequired(DownloadError): ...      # нужен логин или cookies отвергнуты
class RateLimited(DownloadError): ...
class MediaTooLarge(DownloadError): ...
class DownloadTimeout(DownloadError): ...
class NoMedia(DownloadError): ...            # публикация без поддерживаемых медиа
class DownloadFailed(DownloadError): ...     # прочее (в т.ч. ошибка FFmpeg)
# routing.py: class UnsupportedLink(DownloadError)  # изменено в части B: наследник DownloadError,
#                                                   # pipeline ловит одним except

# routing.py
class DownloaderRegistry:
    def __init__(self, by_platform: Mapping[Platform, Downloader]) -> None: ...
    def for_link(self, link: Link) -> Downloader: ...   # KeyError не наружу: UnsupportedLink

# sending.py
@dataclass(frozen=True) class SendVideo: item: MediaItem; caption: str | None
@dataclass(frozen=True) class SendPhoto: item: MediaItem; caption: str | None
@dataclass(frozen=True) class SendAlbum: items: tuple[MediaItem, ...]; caption: str | None
@dataclass(frozen=True) class SendText: text: str
type Send = SendVideo | SendPhoto | SendAlbum | SendText
def plan_sends(result: DownloadResult, limits: TelegramLimits) -> list[Send]: ...
async def send(bot: Bot, chat_id: int, sends: Sequence[Send], reply_to: int | None) -> None: ...
```

Поля `MediaItem` (размеры, длительность) — заполняются из ffprobe (решение 5); нужны ли они
Telegram — `probe_send_media.py`.

## 8. Риски

- **Instagram на VPS ведёт себя иначе** (логин-стена, 429, checkpoint для аккаунта): на этапе
  развёртывания дымовые тесты на VPS до включения бота; варианты — cookies обязательны, снижение
  частоты запросов, прокси (опция yt-dlp `proxy` из переменной окружения; цена — платный
  резидентный прокси и ещё один секрет). Решение — по результату дымовых тестов на VPS.
- **Путь к фото Instagram держится на недокументированном** (решение 6): поведение
  `ignore_no_formats_error`, порядок `thumbnails` и маркер размера в `stp` могут смениться с
  обновлением yt-dlp или Instagram. Ловят дымовые тесты (пост-фото, смешанная карусель; короткая
  сторона скачанного фото ≥ 600 px) и `WARNING` в журнале бота. Сломалось — gallery-dl как библиотека
  (новая зависимость) или отказ пользователю для фото-элемента с остальными элементами карусели.
- **YouTube требует JS-рантайм / PO-token, или блокирует IP дата-центра** («Sign in to confirm
  you're not a bot»): проба 5 на Mac покажет первое; второе — только на VPS (cookies отдельного
  аккаунта Google или прокси; решение на этапе развёртывания).
- **Лимит 52 428 800 байт узкий** (частые `MediaTooLarge` или 720p неприемлем) — решение 21.
- **`scripts/test-hooks.sh` написан под BSD/bash 3.2 и может упасть на Linux в CI**: чинить
  переносимостью; если не выходит — job `hooks` на `macos-latest` (дороже по минутам).
- **Действия GitHub (`actions/checkout`, `astral-sh/setup-uv`) закреплены по тегам, а не по SHA**:
  тег можно переместить. Закрепление по SHA — отложено (ревью части A), вернуться на этапе
  развёртывания или при добавлении секретов в CI; сейчас у workflow права `contents: read`, секретов
  нет.
- **409 Conflict в пробе 0** — где-то жив другой экземпляр со старым токеном: стоп, решение за
  пользователем (`revoke` токена в BotFather = новый токен; бот остаётся в группах).
- **Поток yt-dlp не прерывается мгновенно** — решение 8. **Подтверждено пробой в части B:**
  progress-hook не вызывается на фазе извлечения; принят вариант «ждать поток» (время ответа =
  тайм-аут + хвост извлечения, `WARNING` после порога, семафор держится до конца потока).
- **Cookies в фикстурах или выводе проб**: yt-dlp кладёт их в `formats[].cookies` и
  `http_headers`. Нужны **обе меры вместе**: `scrub()` (решение 20a) убирает их механически до
  записи — но работает только по известным ключам и пропустит новое поле yt-dlp; правило gitleaks
  на `sessionid` (решение 18) ловит значение в любом месте — но только при коммите и только по
  шаблону. Одна мера без другой оставляет дыру.
- **Шаблон токена не подходит к настоящему токену / cookies не ловятся** — положительный контроль
  на настоящих `.env` и `data/instagram.txt` (решение 18) до первого кода с токеном.
- **yt-dlp меняет формат ошибок** — перевод ошибок опирается на тексты из проб; незнакомая ошибка →
  `DownloadFailed` (общий текст пользователю), дымовые тесты ловят смену формата.

  **Добавлено по ревью части B — `stop_grace_period` в compose.** Остановка бота: `run` ждёт потоки
  yt-dlp до `THREAD_GRACE` (60 с), `ThreadRunner.close()` их не ждёт, а выход интерпретатора ждёт
  живой поток пула без ограничения. Значение по умолчанию (10 с) короче порога — Docker убьёт
  процесс раньше, чем `run` дождётся потоков и запишет `ERROR`. Поэтому
